# Внутрішні нотатки — не для клієнтки

Дата: 25 вересня 2026

Тут зібрано все, що прибрано з клієнтських специфікацій (01–05), щоб нічого
не загубилося: відкриті питання, суперечності в дизайні, розбіжності між
прототипом і специфікацією та робочі примітки. Історія змін і повний текст
рішень Р-01…Р-14 — у [`CHANGELOG-2026-09-25.md`](../CHANGELOG-2026-09-25.md),
завдання для Claude Design — у [`PROTOTYPE-CHANGES-BRIEF.md`](../PROTOTYPE-CHANGES-BRIEF.md).

## 1. Відкриті питання до Марини / юриста

| # | Питання | Хто вирішує | Що блокує |
|---|---|---|---|
| В-01 | Cost/tax tables для Кіпру та Іспанії (transfer tax / VAT, stamp duty, legal/notary, щорічні податки) | Марина + податковий консультант | запуск на реальних даних |
| В-02 | Остаточна матриця документів по країнах (чи обов'язкові building permit і escrow) | Марина + юрист | публікацію реальних проєктів |
| В-03 | Юридичні тексти, контролер даних, строки зберігання, subprocessors | юрист | запуск |
| В-04 | Перелік погоджених порталів і умови використання їхніх даних | Марина | підключення збору оренди (MK-10) |

У клієнтських документах ці пункти подано нейтрально — як кроки процесу
(«офіційні джерела, перевірені консультантом», «текст готує юрист»,
Phase 0 «Підготовка даних»), без позначки «відкрито».

## 2. Нові питання, що з'явилися під час чистки

| # | Питання | Контекст |
|---|---|---|
| В-05 | Як рахуються сценарії оренди **average** і **best case** у калькуляторі та на Compare? | У прототипі best case = 2 × base, це демо. У специфікації написано лише, що сценарій підставляє значення із затвердженої оцінки. Логічний варіант — медіана / верх діапазону вибірки, але це не погоджено |
| В-06 | Approve і Publish проєкту — окремі дії чи одна? | У специфікації 1.0 було «не публікувати автоматично, якщо бізнес не погодить об'єднану дію». У клієнтській версії записано як дві окремі дії — це дефолт, не рішення Марини |
| В-07 | KPI targets у §2 специфікації проєкту | Робочі цифри; раніше була примітка «мають бути підтверджені product owner» |
| В-08 | Формули Financial Snapshot (01 §5.4) | Раніше була примітка «мають бути підтверджені замовником і фінансовим/юридичним експертом». Прибрано, бо Марина читає документ саме для підтвердження — варто прямо спитати |
| В-09 | Analytics provider і consent mode | Потрібно визначити до реалізації |
| В-10 | Діапазон interest rate у калькуляторі | У прототипі обмеження немає |

## 4. Що в прототипі є імітацією

Прибрано зі специфікації проєкту §20.

| Елемент прототипу | Статус |
|---|---|
| Перемикач **PREVIEW STATE** | інструмент демонстрації; у продукт не переноситься, переносяться самі стани |
| Екран **Design notes / Overview** | службовий |
| Екран **User Journeys** (14) | внутрішня діаграма; блок CONFIRMED — джерело бізнес-правил |
| Числа в картках, score, yields | тестові дані |
| Формули калькулятора: acquisition = ціна × 1.08, фіксовані €1 400 витрат, short-let × 1.33, best case = 2 × base, округлення оренди до 25 | демонстраційні, **не** методологія |
| Функція `BREAKDOWN()` / `NET_PTS` | ілюстративні; `NET_PTS` збігається з рубрикою лише в смузі 5–5.99% (net 7.2%: демо 30/30, рубрика 27/30; net 4.7%: демо 15/30, рубрика 18/30) |
| «83 published properties», «12 units declared» | тестові величини |
| Impact preview у Score Editor | ілюстративний перерахунок |
| Прогрес перерахунку (~300 мс крок) | анімація |
| Кнопка **Undo** у черзі | замінюється на `Reopen` / `Correct status` (Р-06) |
| Екрани `02-old`, `03-old` | superseded, у реалізацію не беруться |

## 5. Розбіжності прототипу зі специфікацією, які закриває бриф

У клієнтських документах описано **цільову** поведінку. Прототип поки
показує інакше — це правиться за брифом для Claude Design:

| Де | Прототип зараз | Специфікація |
|---|---|---|
| Екран 28 | «AI-proposed financial estimates» | «Proposed financial estimates» |
| Екран 23 | `Undo` після рішення | `Reopen` / `Correct status` |
| Екран 23 | Hold/Query — лише причина | + follow-up date і відповідальний |
| Екран 23 | фільтр лише за типом | + вік, overdue, статус |
| Екран 13 | повзунок 0–40 | 0–100 + попередження >50% |
| Екран 13 | немає історії версій | компактна таблиця версій |
| Екран 30 | кнопка «View as» | прибрана |
| Екран 07 | бали income за `NET_PTS` | за смугами рубрики |
| — | немає P12, D11, A10, A11, P14b | мінімальні екрани (§6.4) |

## 6. «View as user» — якщо повернеться

Прибрано з FR-11c. Якщо функція знадобиться після MVP — лише read-only
support mode з чотирма умовами: помітний banner на всю сесію, обов'язкова
причина входу, запис в audit log, заборона змінювати дані чи виконувати
чутливі дії. Потребує окремої юридичної оцінки.

## 7. Що ще прибрано як історію змін

Усі позначки «v1.1», «ухвалено 25.09.2026», «у версії 1.0 було»,
«підтверджено прототипом», посилання на Р-xx / В-xx / DEC-xx, журнал рішень
(§19 специфікації проєкту) і розділ «Відкриті рішення» (§14 архітектури БД).
Повна історія — у журналі змін.
