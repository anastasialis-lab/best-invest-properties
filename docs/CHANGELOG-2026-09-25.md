# Журнал змін документації — 25 вересня 2026

Звірення комплекту специфікацій (версія 1.0 від 17.09.2026) із затвердженим
візуальним прототипом Best Invest Properties.

**Що використано як джерело:**

- `project/Best Invest Properties.dc.html` — затверджений прототип, 33 екрани;
- реалізація прототипу в `src/` і робоча версія за посиланням
  <https://anastasialis-lab.github.io/best-invest-properties/>;
- блок `CONFIRMED` на екрані User Journeys прототипу — джерело бізнес-правил;
- `chats/chat1.md`, `chats/chat2.md` — листування щодо дизайну.

**Чого не зроблено і чому:** документи не переписувалися з нуля. Структура,
нумерація розділів і чинні формулювання збережені; змінені лише ті місця, де
версія 1.0 суперечить затвердженому прототипу або не описує його.

> **Застереження щодо листування.** Файли `chats/` фіксують ітерації дизайну
> першої версії прототипу (14→19 екранів, вибір шрифтів, лендінг). Вони
> **старші** за затверджену версію і не містять бізнес-вимог. Друга версія
> прототипу надійшла окремим експортом без супровідного листування, тому
> частина рішень відома лише з самого прототипу.

## 3. Відкриті питання

Питання, без відповіді на які не можна починати відповідну частину build.

### OQ-01 — Канонічна таблиця статусів enquiry ⚠️ висока

Прототип показує **три різні словники** для одного й того самого об'єкта:

| Екран | Словник |
|---|---|
| Admin Dashboard | `New`, `Qualifying`, `Hot lead` |
| Approvals Queue | `AWAITING YOU`, `CONNECTED`, `ON HOLD`, `DECLINED` |
| Developer Leads | `Introduced`, `Awaiting admin approval` |

Канонічний набір `Enquiry Status` в архітектурі БД має 11 значень і не
збігається з жодним із трьох. Потрібна затверджена таблиця відповідності
«канонічний статус → підпис для ролі». Без неї звітність і листи розійдуться.
**Блокує:** FR-10, FR-11, MK-04.

### OQ-02 — Джерело «AI-proposed financial estimates» ⚠️ висока

Екран Project Review показує запропоновані орендну плату й витрати. Специфікація
OpenAI 1.0 прямо забороняє AI пропонувати ці значення. Варіанти: аналітик
вручну / зовнішнє джерело даних / OpenAI. Від відповіді залежить, чи потрібен
новий AI use case, конектор до джерела даних і окремий eval.
**Блокує:** FR-03a, AI-03, тип Financial Input.

### OQ-03 — Джерело орендної оцінки та cost/tax tables ⚠️ висока

Відкрите питання прямо назване на екрані User Journeys самого прототипу:
«Decide where the rental estimate comes from — the calculator needs one credible
source before launch». Без нього калькулятор, net yield, score і порівняння
трьох сценаріїв оренди не мають підстави.
**Блокує:** FR-04, FR-05, Financial Snapshot, весь score.

### OQ-04 — Рубрика нормалізації score ⚠️ висока

Категорій п'ять, ваги відомі, але **правило перетворення значень у бали
відсутнє**. Прототип показує лише готові бали демонстраційного об'єкта.
Потрібно: як рахується кожна категорія, з яких даних, чи ваги різні по країнах.
**Блокує:** FR-03, Score Criterion, публікацію будь-якого score.

### OQ-05 — Версіонування score-моделі

У прототипі немає екрана списку версій моделі та історії публікацій, хоча
архітектура їх передбачає і кнопка «Revert to v3» існує. Також незрозуміло, чи
межа 40% на критерій є бізнес-правилом чи обмеженням контрола.
**Блокує:** A07.

### OQ-06 — Чи реальна кнопка Undo

Під кожним рішенням у черзі затверджень прототип показує «Undo». Для рішень,
після яких надіслано листи з контактами, скасування фізично неможливе. Треба
визначити: це реальна компенсаційна дія з новим Audit Event, чи лише
демонстраційний елемент, який у продукт не переноситься.
**Блокує:** FR-11.

### OQ-07 — Owner і due date для Hold/Query

Специфікація 1.0 вимагає: «No decision disappears on Hold/Query: owner and due
date required». Прототип вимагає лише причину. Також немає фільтрів черги за
віком і виконавцем. Питання: додати поля чи послабити вимогу.
**Блокує:** FR-11, A03.

### OQ-08 — Ролі адміністраторів і «four eyes»

Прототип показує один admin-простір, де publish, contact release і зміна
score-моделі доступні з тих самих екранів. Чинна вимога розділяє support /
reviewer / senior. Треба підтвердити поділ і вирішити, чи потрібне правило
«four eyes» для публікації та зміни моделі.
**Блокує:** §10 безпеки, admin build.

### OQ-09 — Матриця документів по країнах

Прототип позначає частину документів як «TO CONFIRM»: building permit і
escrow. Потрібен затверджений перелік обов'язкових документів окремо для
відкриття акаунта і для публікації проєкту, окремо для Cyprus і Spain.
**Блокує:** D02, D06, Document Requirement.

### OQ-10 — Юридичні рішення

Юридична особа-контролер, строки зберігання, legal basis, cookie і analytics
providers. Додатково: текст Privacy Policy і Terms у прототипі — **чернетка**,
потребує юриста. Окремо потребує юридичної оцінки функція **«View as»** на
екрані User Management (сесія підтримки від імені користувача).
Також: у прототипі немає окремих сторінок Cookie Policy та Investment/AI
Disclaimer, хоча архітектура їх передбачає.
**Блокує:** запуск із реальними даними.

### OQ-11 — Рівень listing

Чи справді інвестор обирає конкретний Unit, а не Project або Unit Type.
Прототип показує картку об'єкта без явної моделі Unit Type, тому підтвердити
ADR-01 з самого прототипу не можна.
**Блокує:** схему БД.

### OQ-12 — Екрани, яких немає в прототипі

Потрібно спроєктувати або свідомо виключити з MVP:

| Екран | Наслідок відсутності |
|---|---|
| Audit & Automation Monitor (A10) | немає де побачити застряглі job; прототип на нього посилається текстом |
| Country/Cost Config (A11) | cost/tax правила доведеться редагувати прямо в базі |
| Enquiry Detail (P12) | інвестор не бачить історію запиту |
| Lead Detail (D11) | забудовник не може зафіксувати результат |
| Cookie Policy, Disclaimers | юридична вимога |

## 4. Суперечності в самому дизайні

Зафіксовані, **не** виправлені самостійно — повний перелік із локалізацією
у `05-design-system.md` §9. Найсуттєвіша:

**D-01** — кнопка «Open full review» на Admin Dashboard має контраст тексту
**2.33:1** при мінімумі 4.5:1 за WCAG 2.2 AA. Виправляється зміною кольору
тексту на білий (дає 4.58:1) або затемненням фону. Потребує рішення Марини,
бо це видима зміна затвердженого дизайну.
